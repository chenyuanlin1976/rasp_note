# AIDL: call flow diagram

The flow diagram illustrates:  
how AIDL (Android Interface Definition Language) facilitates communication  
between a Client App, the Binder driver in the Linux Kernel, and the Server Side (Service).

## AIDL Architecture & Call Flow Diagram

+-----------------------------------------------------------------+
| **CLIENT PROCESS**                                              |
|                                                                 |
|  [ Client App Code ]                                            |
|         │                                                       |
|         V                                                       |
|  [ Proxy (`Stub.Proxy`) ]  <--- Implements AIDL Interface       |
|         │                                                       |
|         │ 1. Marshalls data (Parcel)                            |
|         │    & invokes IPC transaction                          |
|         V                                                       |
|  [ `libbinder` (User Space) ]                                   |
+---------│-------------------------------------------------------+
          │
          │ 2. `ioctl()` system call (**Binder Driver Interface**)
          V
+-----------------------------------------------------------------+
| **LINUX KERNEL SPACE**                                          |
|                                                                 |
|  [ Binder Driver (`/dev/binder`) ]                              |
|         │                                                       |
|         │ 3. Handles process switching, copies data             |
|         │    from Client buffer to Server buffer                |
|         │    (Zero-copy/ single-copy optimization)              |
|         V                                                       |
|  [ Target Process Binder Thread Pool ]                          |
+---------│-------------------------------------------------------+
          │
          │ 4. Delivers transaction to receiving thread
          V
+-----------------------------------------------------------------+
| **SERVER PROCESS**                                              |
|                                                                 |
|  [ `libbinder` (User Space) ]                                   |
|         │                                                       |
|         V                                                       |
|  [ Stub (`Binder subclass`) ] <--- Unmarshalls data (Parcel)    |
|         │                                                       |
|         V                                                       |

|         │                                                       |

          V

          │
          V

## Step-by-Step Breakdown

1. Client Invocation (Proxy):
   + The client app calls a method on the local interface (generated by AIDL). Under the hood, this triggers the Proxy class.
   + The Proxy packs (marshalls) the method arguments into a container called a Parcel.
2. Entering the Kernel (libbinder & Binder Driver):
   + The Proxy passes the Parcel to libbinder, which makes an ioctl() system call into the Linux Kernel's Binder Driver (/dev/binder).
3. Kernel IPC Routing:
   + The Binder driver in the kernel handles the heavy lifting of IPC.  
     It finds the destination process, allocates memory in the target process, and copies the transaction data directly  
     (using a shared memory mechanism that avoids multiple user-kernel space copies).
4. Server Dispatch (Stub):
   + A thread from the server's Binder Thread Pool wakes up to handle the incoming transaction.
   + The framework hands the data to the Stub class (the server-side code generated by AIDL).
5. Execution:  
   The Stub unpacks (unmarshalls) the Parcel and invokes the actual method implemented by your Server Side service logic.
6. Returning the Result:  
   + If it's a synchronous call (the default in AIDL, unlike oneway),  
     the server computes the result, marshalls the return values into a reply Parcel,  
     and sends it back through the kernel driver to the client.
