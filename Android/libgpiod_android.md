# libgpiod on Android

libgpiod works on Android the same way it does on Linux: the kernel provides `/dev/gpiochipN`, and libgpiod is a user-space library on top of it.
AOSP does **not** include it, though, and access is restricted by permissions and SELinux.
This note covers how to add it, how to test a pin from the shell, and how to use it from a service.
For the library and tools themselves, see [../Linux/libgpiod_intro.md](../Linux/libgpiod_intro.md).

## 1. Add libgpiod to the AOSP tree

Put the source, for example **libgpiod v1.6.x** (what the notes in this repo use), under `external/libgpiod/` or `vendor/<you>/libgpiod/`.
Then add an `Android.bp`. A sketch for v1:

```bp
cc_library {
    name: "libgpiod",
    vendor_available: true,             // HALs on /vendor link it
    srcs: ["lib/*.c"],
    local_include_dirs: ["include"],
    export_include_dirs: ["include"],
    cflags: [
        "-D_GNU_SOURCE",
        "-DGPIOD_VERSION_STR=\"1.6.4\"",   // normally generated by autotools
        "-Wno-unused-parameter",
    ],
}

// Command-line tools, for bring-up and debugging (don't ship them in user builds)
cc_defaults {
    name: "gpiod_tools_defaults",
    vendor: true,
    srcs: ["tools/tools-common.c"],
    local_include_dirs: ["tools"],
    shared_libs: ["libgpiod"],
    cflags: ["-D_GNU_SOURCE", "-DGPIOD_VERSION_STR=\"1.6.4\""],
}
cc_binary { name: "gpiodetect", defaults: ["gpiod_tools_defaults"], srcs: ["tools/gpiodetect.c"] }
cc_binary { name: "gpioinfo",   defaults: ["gpiod_tools_defaults"], srcs: ["tools/gpioinfo.c"] }
cc_binary { name: "gpioget",    defaults: ["gpiod_tools_defaults"], srcs: ["tools/gpioget.c"] }
cc_binary { name: "gpioset",    defaults: ["gpiod_tools_defaults"], srcs: ["tools/gpioset.c"] }
cc_binary { name: "gpiofind",   defaults: ["gpiod_tools_defaults"], srcs: ["tools/gpiofind.c"] }
```

```make
# device.mk: tools only on eng/userdebug
PRODUCT_PACKAGES_DEBUG += gpiodetect gpioinfo gpioget gpioset gpiofind
```

Kernel requirements: `CONFIG_GPIO_CDEV=y`, plus `CONFIG_GPIO_CDEV_V1=y` for libgpiod v1.
If you use libgpiod v2, the kernel must be **5.10+**, and the `Android.bp` needs the v2 source file list.

## 2. Test a pin from the shell (userdebug)

By default, `/dev/gpiochip*` is root-only, and the `shell` SELinux domain can't open it.
For bring-up, use a root shell:

```shell
adb root && adb shell
gpiodetect                         # gpiochip4 [gpio4] (32 lines) ...
gpioinfo gpiochip1                 # names, directions, and which lines are "used" (owned)
gpiofind WIFI_PWR_EN               # -> "gpiochip1 12"; needs gpio-line-names in the device tree
```

Example: a Wi-Fi power-enable pin on gpiochip1, line 12:

```shell
gpioset --mode=signal gpiochip1 12=0 &   # power off; v1 needs --mode=signal (or wait) to KEEP driving it
gpioget gpiochip1 12                     # NOTE: requests the line as input -> only for lines nobody drives
kill %1                                  # release
gpioset --mode=signal gpiochip1 12=1 &   # power on
dmesg | tail; ip link                    # did the Wi-Fi interface come up?
```

+ A plain `gpioset gpiochip1 12=1` (v1) releases the line as soon as it exits. After that, the level is no longer guaranteed.
+ If `gpioset` fails with **`Device or resource busy`**, a kernel driver owns the pin (for example, the Wi-Fi driver through `enable-gpios`).
  Then control power through that driver (rfkill or sysfs), or remove the property from the device tree.
  See [AIDL_HAL.md](AIDL_HAL.md#5-describing-the-gpio-in-the-device-tree-dtsi).
+ If it fails with `Permission denied` even as root, check `adb shell getenforce` and `dmesg | grep avc`.

## 3. Use it from a service (production)

Apps and the `shell` user never touch `/dev/gpiochip*` in a product.
A **native vendor HAL** links `libgpiod`, owns the lines, and exposes a **stable AIDL** interface:

```text
App / system service --Binder (AIDL)--> vendor GPIO HAL (C++, NDK backend) --libgpiod--> /dev/gpiochipN
```

AIDL itself never talks to the kernel or the device tree. It is only the contract between the caller and the HAL process.
Everything needed is already written up:

| Topic | Note |
| --- | --- |
| Wi-Fi power HAL example (interface, C++ with libgpiod, device-tree options) | [AIDL_HAL.md](AIDL_HAL.md) |
| Complete GPIO HAL: `.aidl`, service, `Android.bp`, `.rc`, `ueventd.rc`, VINTF, SELinux | [AIDL_impl_gpio_cxx.md](AIDL_impl_gpio_cxx.md) |
| Generic AIDL HAL plumbing and clients | [AIDL_HAL_impl.md](AIDL_HAL_impl.md) |
| Why no JNI is needed | [HAL_libgpiod.md](HAL_libgpiod.md#2-do-i-need-jni-native-aidl-hal-vs-jni) |
| Exposing it to 3rd-party apps | [AIDL_3rdParty_app.md](AIDL_3rdParty_app.md) |
| sysfs vs chardev, AOSP checklist | [HAL_libgpiod.md](HAL_libgpiod.md) |

Rules that those notes follow, and that this note's old example broke:

+ Use a `vendor.<company>.hardware.*` package (`android.hardware.*` is reserved for Google), with `@VintfStability`.
+ Use the **NDK backend** (`ndk::ScopedAStatus`) for a vendor HAL, not the cpp backend (`binder::Status`).
+ Report errors **either** through the status (`fromServiceSpecificError`) **or** through a return value, not both.
+ Keep output lines requested for the service's lifetime, and don't re-request an output line as input to read it.
