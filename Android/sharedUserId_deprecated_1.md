# deprecated sharedUserId: alternative

To move away from the deprecated `sharedUserId` and safely access data or system components across different processes or apps,  
Android provides robust Inter-Process Communication (IPC) mechanisms.

The 2 primary methods are

+ **Content Providers with URI Permissions** (best for sharing files and structured data).
+ **AIDL/ Bound Services** (best for executing methods and business logic across processes).

## Method 1: Content Providers with URI Permissions

A Content Provider manages access to a structured set of data and shares it securely using `content://` URIs.  
By default, other apps cannot access your provider unless you explicitly grant them temporary permissions.

### 1. How it works (The Workflow)

1. The Provider App defines a **Content Provider** in its manifest with `android:exported="true"` and `android:grantUriPermissions="true"`.
2. The Client App queries the provider or requests a specific file/data URI.
3. The Provider App grants temporary read/write access to that specific URI using an Intent flag  
   (`FLAG_GRANT_READ_URI_PERMISSION`) or programmatic calls (`context.grantUriPermission()`).
4. The Client App reads the data using **ContentResolver** and loses access once the task is done (or when the grant expires).

### 2. Code Example

+ In the Provider App's `AndroidManifest.xml`:

```xml
<provider
    android:name=".MySystemDataContentProvider"
    android:authorities="com.example.system.provider"
    android:exported="true"
    android:grantUriPermissions="true">
    <!-- Optional: restrict who can access via custom permissions -->
</provider>
```

+ Granting Permission & Sending Data (Provider side):

```kotlin
val dataUri = Uri.parse("content://com.example.system.provider/secure_data/item1")

val intent = Intent().apply {
    data = dataUri
    // Grant temporary read permission to the target client app
    addFlags(Intent.FLAG_GRANT_READ_URI_PERMISSION)
}

// If returning data via setResult or sending to another component:
context.grantUriPermission("com.example.clientapp", dataUri, Intent.FLAG_GRANT_READ_URI_PERMISSION)
```

+ Reading Data (Client side):

```kotlin
val uri = Uri.parse("content://com.example.system.provider/secure_data/item1")

// Query the ContentProvider safely
val cursor = context.contentResolver.query(uri, null, null, null, null)
cursor?.use {
    if (it.moveToFirst()) {
        val dataValue = it.getString(it.getColumnIndexOrThrow("data_column"))
        // Use your data securely here
    }
}
```

## Method 2: AIDL (Android Interface Definition Language) & Bound Services

If you need to perform actions, run complex business logic, or stream data streams across processes rather than just querying flat records,  
AIDL is the standard solution. It acts like a remote procedure call (RPC).

### a. How it works (The Workflow)

1. Define an Interface (.aidl): Both apps agree on an interface file defining what functions can be called (e.g., `getData()`, `performAction()`).
2. Implement the Service: The providing app creates a Service that implements this AIDL stub and exports it,  
   usually protected by a signature-level permission so only apps signed with your certificate can bind to it.
3. Bind from Client: The client app binds to the service using `bindService()`, receives the IBinder interface object,  
   and calls methods directly as if they were local functions.

### b. Code Example

+ Step 1: Create IMyService.aidl (placed in both apps under the same package structure):

```java
package com.example.ipc;

interface IMyService {
    String getSecureSystemData();
}
```

+ Step 2: Implement the Service (Provider App):

```kotlin
class MyRemoteService : Service() {
    // Implement the stub generated by the AIDL file
    private val binder = object : IMyService.Stub() {
        override fun getSecureSystemData(): String {
            // Perform security checks if needed (e.g., check calling UID)
            return "Confidential System Data"
        }
    }

    override fun onBind(intent: Intent): IBinder {
        return binder
    }
}
```

+ Manifest configuration for the Service: Ensure it is protected by a signature permission so unauthorized apps cannot bind to it:

```xml
<service
    android:name=".MyRemoteService"
    android:exported="true"
    android:permission="com.example.permission.ACCESS_SYSTEM_SERVICE">
    <intent-filter>
        <action android:name="com.example.action.BIND_SERVICE" />
    </intent-filter>
</service>
```

### Step 3: Bind and Call (Client App):

```kotlin
var myService: IMyService? = null

private val connection = object : ServiceConnection {
    override fun onServiceConnected(name: ComponentName?, service: IBinder?) {
        myService = IMyService.Stub.asInterface(service)
        // Safely call the method across processes!
        val data = myService?.secureSystemData
    }

    override fun onServiceDisconnected(name: ComponentName?) {
        myService = null
    }
}

// Bind to the service
val intent = Intent("com.example.action.BIND_SERVICE").apply {
    setPackage("com.example.providerapp")
}
context.bindService(intent, connection, Context.BIND_AUTO_CREATE)
```

## Why these approaches are better than sharedUserId

+ Sandboxed Isolation: Each app keeps its own private Linux UID and folder storage. You explicitly choose what to expose.
+ Granular Control: Instead of giving an app unrestricted access to everything in another app's data folder, you only expose specific URIs or methods.
+ Security Permissions: You can enforce `android:protectionLevel="signature"` on your Content Providers or Services,  
  ensuring that only apps signed with your exact build keys can talk to them.

## access system data on Android 14

If you are referring to accessing restricted system data or other apps' private internal data storage on Android 14  
(such as `/data/data/` or restricted subfolders like `Android/data/`),  
the landscape has become extremely tight due to aggressive privacy and security enhancements.

Depending on whether you mean as an app developer or as a user/power user, here is how data access is handled on Android 14:

### 1. From a Developer's Perspective (Building Apps)

If you are writing code and want to access or share system-level/other app data,  
you cannot bypass the application sandbox. Android 14 completely enforces process isolation:

+ No `sharedUserId`: As discussed, trying to use sharedUserId on Android 14 is heavily deprecated or ignored  
  (sharedUserMaxSdkVersion forces apps into individual sandboxes).
+ Target SDK 34 Restrictions: If your app targets Android 14 (API 34), restrictions on implicit intents, stricter package visibility  
  (`<queries>` element in the manifest), and blocked file path sharing make it impossible to casually read other apps' directories.
+ The Correct Approach: If you need data from another app or system component,  
  you must use **Content Providers** with explicit URI permissions (`FLAG_GRANT_READ_URI_PERMISSION`) or  
  **AIDL/Bound Services** where the owner explicitly hands over data via an API call.

### 2. From a Power User/ File Manager Perspective (Accessing Android/data)

If you are trying to access protected directories like Android/data/ on internal storage using a file manager app on Android 14,  
standard file browsing APIs are blocked by the OS.  

The primary methods to access or manage that data on Android 14 include:

+ USB MTP (Connecting to a Computer):  
  Plugging your phone into a PC or Mac via USB and browsing the device storage using file transfer mode  
  still permits viewing many directories that on-device file managers cannot see.
+ ADB (Android Debug Bridge):  
  Using command-line tools via a computer (`adb shell` or specialized ADB file explorers)  
  allows developers and power users to interact with device directories.
+ Shizuku + Compatible File Manager:  
  Tools like Shizuku (using wireless debugging commands) allow specific file explorer apps  
  to perform elevated system operations safely without needing a full root setup.
